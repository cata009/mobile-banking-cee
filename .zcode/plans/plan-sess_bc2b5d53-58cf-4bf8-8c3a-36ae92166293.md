## Smart History-from-Security-Detail filter

### Goal
Tap **History** inside an Investment **security detail** → open `InvestmentsHistoryScreen` pre-filtered to that product's rows, filter **persists** when switching Transactions ↔ Orders.

### Data key finding
- `security.title` is the join key — it's the only value present on both the `InvestmentCatalogSecurity` AND the history rows (as `title`), AND is **searchable** via existing `historyRowMatchesSearch` (which matches on `title` in both transactions and orders branches).
- `productId` / `security.id` are NOT in the searched field set, so can't be used as a search filter.
- `searchQuery` is **already preserved across tab switches** (no reset effect) and **already applied to both lists** — so persist requirement is free once we seed it.
- Existing precedent: codebase uses **App-level state + prop-drilling** (e.g. `selectedAccountId`, `selectedInvestmentSecurity`), NOT an `initialX` one-shot prop. We follow the same pattern.

### Changes (4 files, all small and isolated)

**1. `src/app/App.tsx`**
- Add state: `const [historyFilterByTitle, setHistoryFilterByTitle] = useState<string | null>(null);` next to other selection state (~line 270).
- Extend `handleInvestmentsHistoryClick` to accept optional `filterByTitle?: string`, set state, then navigate.
- Pass `historyFilterByTitle={historyFilterByTitle}` to `<InvestmentsHistoryScreen>` (line 1014-1016).

**2. `src/app/screens/investments/InvestmentsPortfolioScreen.tsx`**
- Widen prop type `onHistoryClick?: () => void` → `onHistoryClick?: (filterByTitle?: string) => void` (line 45).
- On `InvestmentSecurityDetailScreen` render (line 372), intercept: `onHistoryClick={() => onHistoryClick(selectedSecurity.title)}`.
- **Keep** `onHistoryClick={onHistoryClick}` unchanged on the portfolio-level `InvestmentActionBar` (that History button stays unfiltered — it's not tied to a security).

**3. `src/app/screens/investments/InvestmentSecurityScreens.tsx`**
- Widen prop type `onHistoryClick?: () => void` → `onHistoryClick?: (filterByTitle?: string) => void` (line 35).
- Change action row (line 201) `onClick: onHistoryClick` → `onClick: () => onHistoryClick?.(security.title)`.

**4. `src/app/screens/investments/InvestmentsHistoryScreen.tsx`**
- Extend `InvestmentsHistoryScreenProps` (line 43): add optional `historyFilterByTitle?: string | null`.
- Add mount-only effect that seeds `searchQuery` from `historyFilterByTitle`:
  ```ts
  useEffect(() => {
    if (historyFilterByTitle) setSearchQuery(historyFilterByTitle);
  }, []);
  ```
- No other changes — `searchQuery` already persists across tabs + applies to both lists.

### Resulting behavior
- **Security detail → History** → opens with search bar pre-filled (e.g. `Amundi Climate Focus Fund`), only that fund's rows show.
- **Switch Transactions ↔ Orders** → filter stays (default behavior).
- **Portfolio action bar → History** → opens unfiltered (unchanged).
- **Country change while history open** → existing reset effect clears `searchQuery` (correct: titles may not match new country's securities).

### Known limitation (acceptable for mock data)
Substring matching in `historyRowMatchesSearch` could over-match if one fund title were a substring of another. Current mock data has distinct titles, so this isn't a real issue. Not changing the shared matcher (it would affect manual user search too).

### Why this design is "smart" and clean
- No new filter logic — reuses existing `historyRowMatchesSearch` + `searchQuery`.
- Tab persistence is free (already default).
- Follows existing architectural pattern (App-level state + prop-drilling, exactly like `selectedAccountId`).
- 4 small isolated edits, each declarative and reversible.
- No special productId filter logic — productId doesn't exist on history rows, so I deliberately picked the correct join key (title).
