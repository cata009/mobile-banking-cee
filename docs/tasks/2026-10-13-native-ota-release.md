## Implemented boundaries

The [official HotUpdater Vercel recipe](https://hot-updater.dev/docs/custom/hosting/vercel/) establishes the Postgres/object-storage architecture. Its sample `storages`, `handler` and route-group API differs from installed **1.0.1**. This implementation uses the inspected package exports: `createHotUpdater({database, storage, clientAccess:'public'})`, `handlers.client`, `handlers.admin`, `kyselyAdapter`, and the pinned core SQL schema. It has no client auth plugin or portal password dependency.

`native-update-server/src/boundary.ts` is the only HTTP dispatcher. Public GET/HEAD paths are explicitly restricted to SDK version/catalog/artifact reads. `/admin/` authenticates before SDK dispatch and body parsing, uses constant-time byte comparison, and sets `private, no-store`. Management bodies stop at 1 MiB; unknown/encoded admin aliases never become public management calls. Authorization errors and unexpected failures expose generic responses.

`src/storage.ts` stores under `cee-native/` with protocol `cee-ota-s3`. Every write uses `If-None-Match: *`; an exact retry requires matching stored SHA-256 metadata and length, while different bytes fail. The SDK-required delete method explicitly rejects deletion and never sends `DeleteObject`; patches/pruning remain disabled. This follows the documented [AWS conditional-write mechanism](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html), also supported by [R2's S3 API](https://developers.cloudflare.com/r2/api/s3/api/). Keep credentials limited to this bucket/prefix and deny deletion where the provider supports granular permissions. For S3, enforce conditional writes with bucket policy as a second control. R2 retention/object-lock differs from S3: verify retention separately; do not assume this application adapter controls bucket administrators. Failed/aborted releases can leave immutable orphan objects; approved garbage collection is a separate operator procedure.

The server uses pooled PostgreSQL URLs compatible with Neon, TLS certificate verification, a two-connection local pool and Vercel pool lifecycle attachment. SDK schema fencing rejects missing/stale migrations. `migrations/0001-hot-updater-1.0.1.sql` is generated from the pinned SDK, reviewed/versioned, and checksum-recorded by the operator migration script under a transaction/advisory lock. Requests never provision or migrate a database.

## Git/Vercel commit semantics

The pipeline listens for successful **production** deployment status events. It checks out `github.event.deployment.sha`, not the branch's moving HEAD. The preflight re-reads GitHub's default-branch head and Vercel's authenticated deployment API, requiring matching SHA, project, production target and READY state. It also verifies the exact deployment is currently assigned to `VERCEL_WEB_PRODUCTION_URL` through the [read-only Alias API](https://vercel.com/docs/rest-api/aliases/get-an-alias); a merely staged production build does not qualify. A second verification runs after bundle build/upload immediately before the SDK catalog mutation, rejecting a source SHA or alias assignment that became stale during the build. Vercel supports these events; its documentation now recommends richer dispatch events, but existing `deployment_status` remains supported. See [Vercel for GitHub](https://vercel.com/docs/git/vercel-for-github).

The release also binds local source and submitted bundle metadata to that verified SHA. Preflight requires local Git HEAD to match, rejects tracked/untracked pending changes, rejects hidden tracked changes (`assume-unchanged`/`skip-worktree`), and checks ignored files within authored source/asset directories. Generated dependency/build outputs remain permitted. The production config checks source at load, re-verifies the deployment and local source immediately before the real build adapter runs, and repeats verification immediately before `core.deploy`. Every submitted new bundle must carry the exact verified `gitCommitHash`; republishing a stored bundle cannot bypass this check. The current dirty shared checkout intentionally fails these production checks. Local proof uses its separate config.

The only pending-source exception is the runner's unstaged `native-spike/hot-updater.config.ts` selection: its bytes must exactly equal the production config, whose Git blob must match the verified commit. No arbitrary local overrides, staged replacements or unrelated source edits qualify. The release config refuses alternate mutations (promotion, policy/catalog changes, bundle rewriting/deletion and channel changes); rollback/management require separate reviewed operator tooling. These checks bind a reviewed build to the verified source and its metadata; they do not make native and browser UI rendering identical or make delivery to all devices instantaneous. If another commit/deployment supersedes this one, the stale job fails instead of releasing its bundle. Browser promotion/rollback alone does not automatically revoke a native release.

The pinned CLI has no alternate-config flag. The workflow selects `hot-updater.production.config.ts` by copying it over the default filename **only inside its disposable reviewed runner checkout**. Local shared files are never replaced. The production factory requires explicit HTTPS, original signing identity, channel `demo-preview`, approved fingerprint and a real deployment event; it cannot load loopback proof secrets. Windows CI matches the host used to produce the currently approved SDK fingerprint; verify cross-host SDK fingerprint equivalence before switching build OS.

## Limits and native exceptions

Hono is a first-class [Vercel backend](https://vercel.com/docs/frameworks/backend/hono). This project sets a 60-second function limit. Vercel's request/response cap is [4.5 MB](https://vercel.com/docs/functions/limitations), so archives never proxy through a Function. The adapter caps individual uploads at 512 MiB and grants one-hour object read URLs. Large archives/assets, database quotas/connections, storage egress, presigned expiration and physical-device download recovery still require provider/device acceptance testing.

Presigned URLs are transient descriptors, never persisted release identities. Postgres stores `cee-ota-s3://` manifest/asset references. In the installed SDK 1.0.1, `core/reads.mjs` calls `resolveManifestArtifacts` for every artifact request; `db/updateArtifacts.mjs` resolves the manifest, every asset and optional archive through the adapter's `getDownloadUrl`. The artifact handler returns `Cache-Control: private, no-store`. Catalogs hold release IDs/policies, not download URLs; their origin memo lasts five seconds and CDN caching can expose catalog changes up to 15 seconds later. Keep the production rewrite/proxy from adding a cache to artifact descriptors. A local genuine SDK/PGlite regression advances the signer clock eight weeks and verifies fresh URLs for the same unchanged stored bundle, plus URL-free catalog contents. A separate local AWS presigner regression checks the one-hour expiry. Neither test contacts object storage. A device that delays/resumes beyond expiry must request a fresh artifact descriptor; verify this interrupted-download path on a physical device before activation.

JS/assets can update only when their native fingerprint and signing key match the installed base. Kotlin/Java modules, SDK/native dependencies, native permissions, providers/activity configuration, Android styles/fonts/icons, or trust-anchor/endpoint changes require a new reviewed base APK as applicable. Keep package ID/certificate stable and increase the native version code for distributed base upgrades. App-store policy and iOS builds are separate release work; no iOS delivery proof is claimed.

The app stages compatible INSTALL downloads while users edit and applies only at its guarded Home safe point after persistence flush. SDK USE_BUILTIN commits are also deferred to that point. HotUpdater handles pending-launch verification/rollback; server-side catalog rollback and device crash-recovery should be acceptance-tested before activation. Current source/pixel parity and phone-wide biometric/keyboard acceptance are not asserted by this server preparation.
